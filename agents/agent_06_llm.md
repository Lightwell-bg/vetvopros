# Agent 06 — LLM Integration

## 1. Цель

Реализовать клиент вызова LLM (OpenAI-compatible API) для чат-модели с настраиваемым идентификатором модели (в ТЗ: ориентир **ChatGPT / GPT-5.4** — фактическое имя задаётся в `config.ini` / env), загрузкой системного промпта из файла и устойчивостью к ошибкам.

## 2. Контекст

Промпты и пути: [09_config_and_env.md](../09_config_and_env.md); безопасная генерация: [08_specialists_and_medical_flows.md](../08_specialists_and_medical_flows.md).

## 3. Что уже готово

- `config/settings`, каркас сервисов.

## 4. Что именно нужно сделать

- `LlmService` с методами:
  - `complete_with_system(system_prompt, user_message, **kwargs) -> str`
  - поддержка отдельных путей для сценариев анализов (загрузка файлов промптов).
- Таймауты, ретраи (ограниченно), обработка rate limit.
- Не логировать полный контент при включённом «reduced logging» в prod (конфигурируемо).
- Использование `LLM_BASE_URL`, ключа из `.env`, `chat_model` из конфига.

## 5. Какие файлы можно менять

- `src/medvopros/services/llm_service.py`, `src/medvopros/utils/**`, тесты с моками HTTP.

## 6. Какие файлы нельзя менять

- Документацию продуктовых MD без запроса; не встраивать системный промпт в код как единственный источник.

## 7. Зависимости

- **После** agent_02; интеграция в `AnswerService` совместно с agent_05 и agent_09.

## 8. Критерии завершения

- Успешный вызов к тестовому endpoint с реальным ключом (вручную) или мок-тестом.
- Ошибки сети не роняют процесс бота; возвращается контролируемое исключение или Result-type.

## 9. Формат отчёта агента

- **Что сделано**
- **Какие файлы изменены**
- **Что проверить вручную** (модель, лимиты API)
- **Риски** (стоимость, задержки, политика хранения логов)
- **Проверка успешности этапа** — обязательно **последним разделом** отчёта (`agents/report_agent_06_llm.md`): заполнить п. 10; в логах отчёта не хранить полные промпты с ПДн.

## 10. Шаблон финального раздела отчёта: «Проверка успешности этапа»

### Проверка успешности этапа (Agent 06 — LLM)

| Шаг | Действие | Ожидание | Результат |
|-----|----------|----------|-----------|
| 1 | Юнит-тест с моком HTTP (если есть) | Парсинг ответа, таймауты обрабатываются | OK/FAIL/N/A |
| 2 | Интеграционный вызов: короткий запрос к реальному API с тестовым ключом | Ответ непустой, модель = значение из `config.ini` / env | OK/FAIL |
| 3 | Загрузка `prompts/system_prompt.md` с диска | Содержимое подмешивается в запрос (проверка логом/отладкой или тестом) | OK/FAIL |
| 4 | Искусственно занизить таймаут | Ошибка не роняет процесс; исключение/Result задокументированы | OK/FAIL |
| 5 | Неверный ключ (временно) | Понятная ошибка без утечки ключа в ответ пользователю | OK/FAIL |
| 6 | Указать в отчёте: `LLM_BASE_URL` (если не дефолт), имя модели, latency одного запроса | Для Team Lead | OK/FAIL |

Этап **успешен**, если 2 и 3 — OK (или 1+3 при полном отказе от live-вызова с обоснованием в отчёте).

**Не** вставлять в отчёт `LLM_API_KEY` / `OPENAI_API_KEY`.
