# Agent 01 — Architect / Architecture Review

## 1. Цель

Проверить согласованность архитектурной документации и предлагаемой структуры кода с ТЗ; выявить слабые места, риски масштабирования и противоречия между документами `00`–`12`.

## 2. Контекст

Проект: медицинский справочный Telegram-бот с RAG (PostgreSQL + pgvector), LLM fallback, админкой, биллингом и medical guardrails. Документация в корне репозитория: [00_project_overview.md](../00_project_overview.md) … [12_acceptance_checklist.md](../12_acceptance_checklist.md).

## 3. Что уже готово

- Набор проектных MD-файлов и дерево каталогов в [02_project_structure.md](../02_project_structure.md).
- Описание БД, RAG, бота, админки, биллинга.

## 4. Что именно нужно сделать

- Сверить модули и потоки из [01_system_architecture.md](../01_system_architecture.md) с [02_project_structure.md](../02_project_structure.md).
- Оценить разделение слоёв (handlers vs services vs repositories).
- Предложить 3–7 конкретных улучшений (без переписывания всего ТЗ): например webhook vs polling, очередь индексации, контракт `AnswerService`.
- Зафиксировать выводы в отчёте агента; при необходимости предложить правки формулировок в документации (отдельным MR/задачей).

## 5. Какие файлы можно менять

- Только документацию: `00`–`12`, при необходимости `README.md` (раздел «Архитектура»), **если** согласовано с владельцем репозитория.

## 6. Какие файлы нельзя менять

- Исходный код приложения (если он уже появился) — в рамках этой задачи не рефакторить без отдельной постановки.

## 7. Зависимости

- Нет зависимости от реализации кода; опционально — черновик кода для фактической проверки.

## 8. Критерии завершения

- Есть письменный отчёт с рисками, улучшениями и явным списком «противоречий документации / нет».
- Рекомендации по масштабированию и границам MVP согласованы с [10_mvp_scope.md](../10_mvp_scope.md).

## 9. Формат отчёта агента

- **Что сделано:** краткий список проверок.
- **Какие файлы изменены:** пути или «нет».
- **Что проверить вручную:** владельцу продукта / Team Lead.
- **Риски:** топ-5 с приоритетом.
- **Проверка успешности этапа** — обязательно **последним разделом** отчёта (файл `agents/report_agent_01_architect.md` или обновление существующего): заполнить раздел по шаблону из п. 10; указать для каждого шага «пройдено / не пройдено» и краткий вывод. **Не** вставлять секреты и токены.

## 10. Шаблон финального раздела отчёта: «Проверка успешности этапа»

Агент **копирует** заголовок ниже в конец своего отчёта и заполняет таблицу/чеклист результатами.

### Проверка успешности этапа (Agent 01 — Architect)

1. **Отчёт создан и сохранён** в `agents/report_agent_01_architect.md` (или указано имя файла).
2. **Таблица противоречий** в отчёте заполнена: для каждой строки указан статус (устранено / открыто / не применимо).
3. **Выборочная сверка документов:** открыты [01_system_architecture.md](../01_system_architecture.md) и [02_project_structure.md](../02_project_structure.md) — поток «Handlers → AnswerService → …» и наличие слоя `medical/` не противоречат друг другу (кратко зафиксировать вывод: «согласовано» / «найдено расхождение: …»).
4. **Согласованность с MVP:** явная ссылка на [10_mvp_scope.md](../10_mvp_scope.md) и перечень рекомендаций, которые **не** выходят за границы MVP (или помечены как «этап 2»).
5. **Топ-риски** в отчёте содержат не менее 3 пунктов с приоритетом (P1/P2/P3).
6. **Team Lead:** может принять этап, если п. 1–2 выполнены и п. 3 не содержит нерешённых критичных противоречий без плана.

**Команды не обязательны** (документальный этап). При правках в `01`–`12` указать в отчёте дифф или список изменённых файлов для повторной вычитки.
