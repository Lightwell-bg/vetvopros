## Разделение слоёв (краткая оценка)

- **Handlers** — парсинг Telegram, маршрутизация команд, вызов одного-двух сервисов, форматирование ответа пользователю. SQL и бизнес-ветвления RAG/биллинга здесь не держать.
- **Services** — `AnswerService` как единая оркестрация guardrails → billing → RAG → LLM → запись в БД/аудит; `RAGService`/`LLMService` как фасады над `rag/` и API.
- **Repositories** — SQLAlchemy/сырые запросы, транзакции; **db/models** — схема без бизнес-логики.
- **medical/** — правила и классификация red flags; вызывается из `AnswerService`, чтобы тесты и админка могли переиспользовать тот же слой без дублирования в handlers.

Структура `02` этому соответствует; риск — «толстые handlers» при спешной реализации: контролировать code review / `agent_02` + `agent_03`.

## Рекомендации (3–7 улучшений, без переписывания ТЗ)

0. **Специалист в одном боте:** релей сообщений и отдельная квота зафиксированы в `05`, `07`, `08`, `config.ini`; при обзоре интеграций не смешивать с устаревшей моделью «только контакт в конфиге».

1. **Зафиксировать контракт `AnswerService`** в `05_bot_logic.md` или коротком подразделе в `01`: вход (текст, user_id, метаданные сессии), выход (текст ответа, `source`, флаги эскалации, ошибки биллинга). Упростит параллельную работу agent_02 и agent_03.
2. **Webhook vs long polling (aiogram):** в MVP допустим `start_polling` ([10_mvp_scope.md](../10_mvp_scope.md), этап 2 — webhook); в `run_bot.py` заложить переключатель по `config.ini`/env, чтобы не ломать деплой позже.
3. **Очередь индексации:** оставить за этапом 2 ([10_mvp_scope.md](../10_mvp_scope.md)); в MVP — явно описать синхронный ingest с таймаутом и блокировкой документа в админке, чтобы не было двойной индексации.
4. **Единый путь админки к данным:** маршруты FastAPI только через те же `repositories`, что и бот — исключить «протечку» сырого SQL в `routes_*.py`.
5. **Идемпотентность списаний:** при повторной доставке сообщения Telegram кратко описать в `07`/`11`, как избежать двойного списания квоты (идempotency key по `update_id` или аналог).
6. **Наблюдаемость:** в `01` или `09` один абзац: обязательные поля structured log (user hash, source, latency RAG/LLM) для расследований guardrails и биллинга.

## Согласованность с MVP ([10_mvp_scope.md](../10_mvp_scope.md))

- Два процесса (бот + админка), общая БД — соответствует ADR в `01`.
- Очередь индексации и webhook — вынесены в этап 2; рекомендации выше не требуют их в MVP.
- Stub биллинга и RAG+LLM+guardrails — архитектура `02` покрывает без расширения scope.
