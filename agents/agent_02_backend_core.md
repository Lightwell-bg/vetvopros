# Agent 02 — Backend Core

## 1. Цель

Заложить каркас Python-приложения: загрузка конфигурации, логирование, подключение к БД (session factory), базовые сервисные интерфейсы, healthcheck, зависимости проекта.

## 2. Контекст

Архитектура: [01_system_architecture.md](../01_system_architecture.md), структура: [02_project_structure.md](../02_project_structure.md), конфиг: [09_config_and_env.md](../09_config_and_env.md).

## 3. Что уже готово

- Документация и целевое дерево `src/medvopros/`.

## 4. Что именно нужно сделать

- Создать пакет `medvopros` с `config/settings.py` (чтение `config.ini` + `pydantic-settings` / `python-dotenv` для `.env`).
- Настроить структурированное логирование в `utils/logging.py`.
- Реализовать `db/session.py` (engine, session scope); модели могут быть заглушкой до agent_04.
- Добавить `GET /health` (в общем FastAPI app или отдельном минимальном модуле, согласованном с agent_07).
- `requirements.txt` или `pyproject.toml` с зафиксированными основными зависимостями (в т.ч. **aiogram 3.x** для Telegram — реализация бота в agent_03).
- Точки входа `run_bot.py` / `run_admin.py` — каркас с импортом настроек и проверкой env.

## 5. Какие файлы можно менять

- `src/**`, `requirements.txt`, `pyproject.toml`, при необходимости минимальные правки `README.md` (запуск).

## 6. Какие файлы нельзя менять

- Агентские задания `agents/*`, проектные `00`–`12` — без согласования.

## 7. Зависимости

- После или параллельно с ревью agent_01; до полной реализации БД — допустимы заглушки сессии.

## 8. Критерии завершения

- Установка зависимостей и импорт настроек работают.
- Healthcheck отвечает 200 при доступной БД (или явной degraded-политике, задокументированной в отчёте).
- Секреты не читаются из `config.ini`.

## 9. Формат отчёта агента

- **Что сделано**
- **Какие файлы изменены**
- **Что проверить вручную** (переменные `.env`, запуск PostgreSQL)
- **Риски** (например несовместимость sync/async ORM)
- **Проверка успешности этапа** — обязательно **последним разделом** отчёта (`agents/report_agent_02_backend_core.md`): заполнить раздел по шаблону п. 10; для каждого шага — «OK / FAIL», при FAIL — текст ошибки (без секретов).

## 10. Шаблон финального раздела отчёта: «Проверка успешности этапа»

### Проверка успешности этапа (Agent 02 — Backend Core)

Выполнить из **корня репозитория** с активированным venv. В отчёт вставить **фактические** команды и сокращённый вывод (без токенов).

| Шаг | Действие | Ожидание | Результат |
|-----|----------|----------|-----------|
| 1 | `pip install -e .` | Успешная установка | OK/FAIL |
| 2 | Заполнены `.env`: `DATABASE_URL`, для админки сильный `ADMIN_SESSION_SECRET` (не дефолт из примера) | — | OK/FAIL |
| 3 | `python -c "from medvopros.config.settings import get_settings; get_settings(); print('settings_ok')"` | Вывод `settings_ok` | OK/FAIL |
| 4 | `python src/run_bot.py` (с полным набором env для бота: токен, LLM key, `DATABASE_URL`) | Лог с событием успешного каркаса (например `bot_scaffold_ok`), exit 0 | OK/FAIL |
| 5 | В отдельном терминале: `python src/run_admin.py`, затем `curl -s -o - -w "\nHTTP:%{http_code}\n" http://127.0.0.1:8000/health` | HTTP 200, тело с `"database":"up"` или эквивалент | OK/FAIL |
| 6 | Негативный тест: остановить PostgreSQL или временно неверный `DATABASE_URL`, повторить `GET /health` | HTTP 503 (или задокументированный degraded), не «всегда 200» | OK/FAIL |
| 7 | Убедиться, что в `config.ini` нет API-ключей и токенов | Только несекретные параметры | OK/FAIL |

Этап считается **успешным**, если шаги 1, 3, 5, 7 — OK; шаг 6 подтверждает честный healthcheck.
